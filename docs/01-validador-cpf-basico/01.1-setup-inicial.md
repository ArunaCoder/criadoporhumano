# 🏗️ Camada 1: Servidor HTTP de Baixo Nível

**Objetivo:** Entender o protocolo HTTP sem intermediários.

---

## 📋 Decisões Técnicas desta Camada

### Single-Threaded vs Thread Pool

**Decisão:** Implementação single-threaded (bloqueante) inicial.

**Justificativa:**

- Validação de CPF tem resposta <1ms
- Simplicidade de implementação e debugging
- Suficiente para ~1000 req/s (mais que adequado para MVP)
- Evita overhead de criação/destruição de threads
- Evita vulnerabilidade de DoS por thread exhaustion

**Solução ignorada intencionalmente - Thread por conexão:**

```rust
for stream in listener.incoming() {
    std::thread::spawn(move || {
        handle_connection(stream);
    });
}
```

**Custos ignorados:**

- ~2MB de RAM por thread (stack)
- 1000 conexões simultâneas = 2GB RAM
- Overhead de criação: ~50-100µs por thread
- Atacante pode esgotar memória abrindo 100.000 conexões
- Context switching degrada performance sob carga

**Quando mudar:**

- Se profiling mostrar gargalo de CPU
- Se precisar escalar para >5000 req/s
- Solução: thread pool com limite fixo (ex: 8 threads = núcleos de CPU)

**Princípio aplicado:** "Premature optimization is the root of all evil" (Donald Knuth)

### Async/Await (Tokio) vs Blocking I/O

**Decisão:** I/O bloqueante com std lib.

**Justificativa:**

- Zero dependências externas (objetivo do projeto)
- Requests são rápidos (não precisa de alta concorrência)
- Código mais simples e legível
- Suficiente para o caso de uso

**Solução ignorada:** Tokio/async runtime

- **Custo:** +500KB no binário
- **Complexidade:** Curva de aprendizado de async/await
- **Desnecessário:** Para I/O rápido, blocking é mais eficiente

### Módulo HTTP em `backend/shared` vs `backend/api`

**Decisão:** Implementar em `backend/shared/src/http/` (compartilhado entre serviços).

**Justificativa:**

- Código HTTP é reutilizável por múltiplos serviços (api, cli, etc.)
- Mantém separação clara: shared = infraestrutura, api = lógica de negócio
- Facilita testes isolados do parsing HTTP
- Princípio: "Shared code for shared concerns"

**Alternativa considerada:** Implementar dentro de `backend/api/src/http/`

- **Problema:** Duplicação quando adicionar outros serviços
- **Problema:** Dificulta testes unitários do HTTP isoladamente
- **Problema:** Viola DRY (Don't Repeat Yourself)

**Decisão final:** Shared desde o início porque sabemos que teremos múltiplos pontos de entrada (api server, cli tools).

**Princípio aplicado:** "You aren't gonna need it" (YAGNI) - não crie abstração até precisar dela.

#### 💭 Pensamento do Engenheiro

**Objetivo:** Criar um servidor HTTP do zero.

**O que um servidor HTTP precisa fazer?**

1. **Escutar conexões TCP** em uma porta (ex: 8080)
2. **Aceitar clientes** que conectam
3. **Ler dados da rede** (bytes brutos enviados pelo cliente)
4. **Parsear HTTP request** (transformar bytes em estrutura compreensível: método, path, headers, body)
5. **Processar a request** (executar lógica de negócio)
6. **Construir HTTP response** (transformar resultado em estrutura: status code, headers, body)
7. **Serializar e enviar** (transformar estrutura em bytes e enviar pela rede)

**Como organizar esses 7 componentes?**

Essas são **responsabilidades distintas**. Se eu misturar tudo em um arquivo gigante, cada mudança vai afetar centenas de linhas. Vou separar por **função lógica**:

- **`server.rs`** — Responsável por (1) e (2): escuta TCP e aceita conexões
  - Conhece: sockets, `TcpListener`, `TcpStream`
  - Não conhece: o que é HTTP, como parsear, o que fazer com requests

- **`request.rs`** — Responsável por (3) e (4): lê bytes e parseia em `HttpRequest`
  - Conhece: formato do protocolo HTTP (request line, headers, body)
  - Não conhece: o que fazer com a request depois de parseada

- **`response.rs`** — Responsável por (6) e (7): constrói `HttpResponse` e serializa em bytes
  - Conhece: formato do protocolo HTTP (status line, headers, body)
  - Não conhece: de onde vêm os dados da response

**Por que não um único arquivo?**

Eu poderia colocar tudo em `main.rs`, mas:

- **Mudança localizada:** Se o protocolo HTTP mudar (improvável, mas ilustrativo), altero apenas `request.rs` e `response.rs`. O `server.rs` não é afetado.
- **Teste isolado:** Posso testar o parser de request separadamente, alimentando bytes de teste sem precisar de uma conexão TCP real.
- **Reutilização:** Se amanhã eu quiser suportar HTTPS, substituo apenas `server.rs` (TCP → TLS), mantendo o parser intacto.
- **Carga cognitiva:** Quando debugo parsing de headers, abro `request.rs` (150 linhas) em vez de rolar por 800 linhas buscando a função certa.

**Como Rust materializa essa separação?**

Rust usa **módulos baseados em arquivos**. A estrutura física espelha a estrutura lógica:

```
src/
├── main.rs              ← Ponto de entrada (orquestra tudo)
└── http/
    ├── mod.rs           ← "Índice" do módulo (declara submódulos)
    ├── server.rs        ← TCP listener
    ├── request.rs       ← Parser de request
    └── response.rs      ← Builder de response
```

No `mod.rs`, declaro:

```rust
pub mod server;
pub mod request;
pub mod response;
```

Isso torna os submódulos **públicos** para o resto da aplicação. No `main.rs`, importo com `mod http;` e uso `http::server::start_server()`.

**Vantagem técnica oculta:**

O compilador Rust pode **compilar `request.rs`, `response.rs` e `server.rs` em paralelo** se houver núcleos de CPU disponíveis. Um arquivo monolítico compilaria sequencialmente. Em projetos grandes, isso economiza tempo real de build.
