## 1.3 Parser de Request Manual

### Passo 5: Struct HttpRequest

#### 💭 Pensamento do Engenheiro

**Onde estamos?**

Nos passos anteriores, construímos as fundações: o servidor já aceita conexões TCP (Passo 3) e já consegue ler a primeira linha da requisição como texto bruto (Passo 4). Se eu rodar `curl http://localhost:8080`, o servidor imprime `"GET / HTTP/1.1"` no console. Isso funciona, mas é **texto não-estruturado** — para processar essa requisição, eu precisaria fazer `split()` toda vez que quiser saber o método ou o path. Se 10 partes do código precisarem verificar o método, vou fazer parsing 10 vezes. Além disso, só estou lendo a **primeira linha** — headers e body ainda estão ignorados.

**O que preciso agora?**

Preciso de duas coisas: **(1)** ler a requisição **completa** (request line + headers + body), e **(2)** transformar esse texto em uma **estrutura de dados** que o resto do código possa usar sem retrabalho. Em outras palavras, quero que o parsing aconteça **uma vez, no início**, e depois todo mundo trabalhe com dados já validados e organizados. Esse é o momento de criar uma representação interna da requisição — uma struct que encapsula método, path, headers e body — e um parser que transforma bytes brutos nessa struct. Se o parsing falhar (requisição malformada), recuso a requisição antes de processar qualquer lógica. Se passar, garanto que daqui pra frente estou trabalhando com dados válidos.

**O que é uma requisição HTTP?**

Quando um cliente envia uma requisição HTTP, ele está enviando **texto estruturado** seguindo um formato específico:

```
GET /api/users?id=123 HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 42

{"name":"Alice","age":30}
```

Esse texto tem 4 partes:

1. **Request line:** `GET /api/users?id=123 HTTP/1.1` (método, path, versão)
2. **Headers:** Linhas com `chave: valor` (metadados da requisição)
3. **Linha vazia:** Separador entre headers e body
4. **Body:** Dados da requisição (JSON, formulário, etc.)

**Por que criar uma struct ao invés de trabalhar com String?**

Eu poderia manter tudo como `String` e fazer split toda vez que preciso do método ou path. Mas isso tem problemas:

- **Retrabalho:** Se 10 lugares do código precisam do método, vou fazer split 10 vezes
- **Erros:** Cada lugar pode fazer o split diferente (split por espaço? por `\n`? trim?)
- **Tipo fraco:** `String` não comunica intenção — `request` pode ser qualquer texto
- **Validação dispersa:** Validar método HTTP em múltiplos lugares = duplicação

**Uma struct resolve isso:**

- **Parse uma vez:** Transformo bytes → struct no início, resto do código usa struct
- **Tipo forte:** `HttpRequest` comunica que aquilo é uma requisição válida e parseada
- **Acesso direto:** `request.method` em vez de `request.split_whitespace().next()`
- **Validação centralizada:** A struct só existe se passou pelas validações

**Como organizar os 4 componentes em campos?**

Cada parte da requisição se torna um campo:

- **`method: String`** — GET, POST, HEAD, OPTIONS
- **`path: String`** — /api/users, /, /static/style.css
- **`headers: HashMap<String, String>`** — Chave-valor para lookup eficiente
- **`body: String`** — Payload (pode estar vazio em GET)

**Por que HashMap para headers?**

Headers podem vir em qualquer ordem e são consultados por nome:

```rust
// Preciso verificar se tem Content-Type
if let Some(ct) = request.headers.get("content-type") { ... }
```

Três opções existem:

1. **Vec<(String, String)>** — Precisa iterar todos para achar um header específico (O(n))
2. **HashMap<String, String>** (nossa escolha) — Lookup direto por chave (O(1))
3. **Array fixo** — Não funciona, número de headers é variável

HashMap é ideal: lookup instantâneo, tamanho dinâmico, API conveniente (`.get()`, `.contains_key()`).

**Por que método `parse()` ao invés de construtor `new()`?**

Rust tem convenção de nomenclatura:

- **`new()`**: construtor simples que nunca falha (ex: `Vec::new()`)
- **`parse()`**: conversão que pode falhar (ex: `"123".parse::<i32>()`)

Parsear HTTP **pode falhar** (bytes inválidos, linha muito longa, versão não suportada). Logo, a assinatura correta é:

```rust
pub fn parse(reader: &mut BufReader<TcpStream>) -> Result<Self, String>
```

O tipo `Result<T, E>` comunica explicitamente: "esta operação pode dar erro, trate-o".

**Fluxo de uso:**

```rust
// Em handle_connection()
let request = match HttpRequest::parse(&mut reader) {
    Ok(req) => req,              // Sucesso: tenho struct válida
    Err(e) => {                  // Falha: envio erro 400 e retorno
        send_error_response(stream, e);
        return;
    }
};

// Daqui pra frente, request é garantidamente válido
println!("Method: {}", request.method);
println!("Path: {}", request.path);
```

Essa estrutura separa claramente **parsing** (pode falhar) de **processamento** (assume dados válidos).

### Passo 6: Parse da Request Line

#### 💭 Pensamento do Engenheiro

**Onde estamos?**

No Passo 5, criamos a estrutura `HttpRequest` e a assinatura do método `parse()`. Agora temos o "molde" que queremos preencher, mas a função ainda está vazia (`todo!()`). Conseguimos ler a primeira linha da requisição (isso vem do Passo 4 que fizemos em `server.rs`), mas ainda não extraímos as informações dessa linha nem validamos se são legítimas.

**O que preciso agora?**

Preciso **parsear e validar** a request line. Essa linha contém 3 componentes críticos: método HTTP, path e versão. Cada um precisa de validação rigorosa antes de aceitar a requisição. Não posso simplesmente confiar no que o cliente envia — preciso verificar que o método é permitido, que a versão é suportada, e **especialmente** que o path não contém tentativas de ataque. Se qualquer validação falhar, devo rejeitar imediatamente com erro 400. Só depois de todas as validações passarem, posso prosseguir para headers e body.

**Por que validação de path é crítica?**

Path traversal é um dos ataques mais comuns e perigosos em servidores web. O atacante tenta manipular o path para acessar arquivos fora do diretório público:

```
GET /../../../etc/passwd HTTP/1.1     ← Ataque clássico
GET /api/users%2e%2e%2fetc/passwd     ← URL encoding bypass
GET //etc/passwd HTTP/1.1              ← Absolute path abuse
```

**Validação básica (INSUFICIENTE):**

```rust
if path.contains("..") || path.contains("//") {  // ❌ Fácil bypass
    return Err("Invalid path");
}
```

Problemas:

- **URL encoding bypass:** `%2e%2e` = `..` (depois de decode)
- **Não valida paths absolutos:** `/etc/passwd` passa
- **Não normaliza:** `./././etc/passwd` passa

**Validação production-ready (CORRETO):**

Usar `canonicalize()` da std lib para garantir segurança real:

1. **Canonicalização:** Transforma path relativo em absoluto normalizado (resolve `.`, `..`, symlinks)
2. **Verificação de prefixo:** Garante que o path final ainda está dentro do diretório base

**Como funciona:**

- `PathBuf::from("./public")` — Define diretório base permitido
- `.join(path)` — Combina base + path do cliente
- `.canonicalize()` — Resolve `..`, `.`, symlinks → path absoluto real no disco
- `.starts_with(base)` — Verifica que path final ainda está dentro da base

**Por que isso previne ataques?**

- `canonicalize()` **resolve** `..`, `.`, symlinks → path absoluto real
- `starts_with()` **verifica** que path final ainda está em `/caminho/para/public`
- Impossível escapar: qualquer tentativa de `..` é resolvida e depois detectada

**Exemplo:**

```
Base: /var/www/public
Request: /../../../etc/passwd

Após canonicalize: /etc/passwd
starts_with(/var/www/public)? NÃO → REJEITA ✅
```

  ```rust
  use std::env;
  use std::path::{Path, PathBuf};

  // Ler diretório base de variável de ambiente (12-factor app)
  // Default: "./public" (desenvolvimento)
  // Produção: passar PUBLIC_DIR=/var/www/html ao executar
  let base_dir = env::var("PUBLIC_DIR")
      .unwrap_or_else(|_| "./public".to_string());
  let base = PathBuf::from(base_dir);

  // Combinar base + path requisitado
  let requested = base.join(path.trim_start_matches('/'));

  // Canonicalizar (resolve .., symlinks, etc)
  let canonical = requested.canonicalize()
      .map_err(|_| "Invalid path or file not found".to_string())?;

  // CRÍTICO: Verificar que ainda está dentro do base
  let base_canonical = base.canonicalize()
      .map_err(|_| "Failed to resolve base directory".to_string())?;

  if !canonical.starts_with(&base_canonical) {
      return Err("Path traversal detected".to_string());
  }
  ```

  **⚙️ Configuração da Variável PUBLIC_DIR:**

  O código acima usa `env::var("PUBLIC_DIR")` para determinar o diretório base de arquivos servidos. Essa é uma prática de **12-factor app** (config via ambiente), permitindo diferentes diretórios em dev/staging/produção sem alterar código.

  **Default:** Se `PUBLIC_DIR` não estiver definida, usa `"./public"` (relativo ao diretório onde o binário é executado).

  **Importante:** O path é **relativo ao diretório de execução**, não ao local do código-fonte. Sempre rode o servidor do diretório correto ou use path absoluto em produção.

  **Exemplos de uso:**

* **Dev (default)**
  - Comando: `cargo run`
  - Diretório: `./public` (relativo ao `backend/api/`)

* **Dev (custom)**
  - Comando: `PUBLIC_DIR=../frontend/dist cargo run`
  - Diretório: `../frontend/dist`

* **Produção (VPS)**
  - Comando: `PUBLIC_DIR=/var/www/html /opt/app/api`
  - Diretório: `/var/www/html` (path absoluto)

* **Systemd**
  - Comando: `Environment="PUBLIC_DIR=/var/www/html"` no `.service`
  - Diretório: `/var/www/html`

* **Docker**
  - Comando: `docker run -e PUBLIC_DIR=/app/static api`
  - Diretório: `/app/static` (dentro do container)

  **⚠️ Pré-requisito:** O diretório **deve existir** antes de rodar o servidor, senão `canonicalize()` falhará com "Failed to resolve base directory".
