## 1.3 Parser de Request Manual

### Passo 5: Struct HttpRequest

#### 💭 Pensamento do Engenheiro

**Onde estamos?**

Nos passos anteriores, construímos as fundações: o servidor já aceita conexões TCP (Passo 3) e já consegue ler a primeira linha da requisição como texto bruto (Passo 4). Se eu rodar `curl http://localhost:8080`, o servidor imprime `"GET / HTTP/1.1"` no console. Isso funciona, mas é **texto não-estruturado** — para processar essa requisição, eu precisaria fazer `split()` toda vez que quiser saber o método ou o path. Se 10 partes do código precisarem verificar o método, vou fazer parsing 10 vezes. Além disso, só estou lendo a **primeira linha** — headers e body ainda estão ignorados.

**O que preciso agora?**

Preciso de duas coisas: **(1)** ler a requisição **completa** (request line + headers + body), e **(2)** transformar esse texto em uma **estrutura de dados** que o resto do código possa usar sem retrabalho. Em outras palavras, quero que o parsing aconteça **uma vez, no início**, e depois todo mundo trabalhe com dados já validados e organizados. Esse é o momento de criar uma representação interna da requisição — uma struct que encapsula método, path, headers e body — e um parser que transforma bytes brutos nessa struct. Se o parsing falhar (requisição malformada), recuso a requisição antes de processar qualquer lógica. Se passar, garanto que daqui pra frente estou trabalhando com dados válidos.

**O que é uma requisição HTTP?**

Quando um cliente envia uma requisição HTTP, ele está enviando **texto estruturado** seguindo um formato específico:

```
GET /api/users?id=123 HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 42

{"name":"Alice","age":30}
```

Esse texto tem 4 partes:

1. **Request line:** `GET /api/users?id=123 HTTP/1.1` (método, path, versão)
2. **Headers:** Linhas com `chave: valor` (metadados da requisição)
3. **Linha vazia:** Separador entre headers e body
4. **Body:** Dados da requisição (JSON, formulário, etc.)

**Por que criar uma struct ao invés de trabalhar com String?**

Eu poderia manter tudo como `String` e fazer split toda vez que preciso do método ou path. Mas isso tem problemas:

- **Retrabalho:** Se 10 lugares do código precisam do método, vou fazer split 10 vezes
- **Erros:** Cada lugar pode fazer o split diferente (split por espaço? por `\n`? trim?)
- **Tipo fraco:** `String` não comunica intenção — `request` pode ser qualquer texto
- **Validação dispersa:** Validar método HTTP em múltiplos lugares = duplicação

**Uma struct resolve isso:**

- **Parse uma vez:** Transformo bytes → struct no início, resto do código usa struct
- **Tipo forte:** `HttpRequest` comunica que aquilo é uma requisição válida e parseada
- **Acesso direto:** `request.method` em vez de `request.split_whitespace().next()`
- **Validação centralizada:** A struct só existe se passou pelas validações

**Como organizar os 4 componentes em campos?**

Cada parte da requisição se torna um campo:

- **`method: String`** — GET, POST, HEAD, OPTIONS
- **`path: String`** — /api/users, /, /static/style.css
- **`headers: HashMap<String, String>`** — Chave-valor para lookup eficiente
- **`body: String`** — Payload (pode estar vazio em GET)

**Por que HashMap para headers?**

Headers podem vir em qualquer ordem e são consultados por nome:

```rust
// Preciso verificar se tem Content-Type
if let Some(ct) = request.headers.get("content-type") { ... }
```

Três opções existem:

1. **Vec<(String, String)>** — Precisa iterar todos para achar um header específico (O(n))
2. **HashMap<String, String>** (nossa escolha) — Lookup direto por chave (O(1))
3. **Array fixo** — Não funciona, número de headers é variável

HashMap é ideal: lookup instantâneo, tamanho dinâmico, API conveniente (`.get()`, `.contains_key()`).

**Por que método `parse()` ao invés de construtor `new()`?**

Rust tem convenção de nomenclatura:

- **`new()`**: construtor simples que nunca falha (ex: `Vec::new()`)
- **`parse()`**: conversão que pode falhar (ex: `"123".parse::<i32>()`)

Parsear HTTP **pode falhar** (bytes inválidos, linha muito longa, versão não suportada). Logo, a assinatura correta é:

```rust
pub fn parse(reader: &mut BufReader<TcpStream>) -> Result<Self, String>
```

O tipo `Result<T, E>` comunica explicitamente: "esta operação pode dar erro, trate-o".

**Fluxo de uso:**

```rust
// Em handle_connection()
let request = match HttpRequest::parse(&mut reader) {
    Ok(req) => req,              // Sucesso: tenho struct válida
    Err(e) => {                  // Falha: envio erro 400 e retorno
        send_error_response(stream, e);
        return;
    }
};

// Daqui pra frente, request é garantidamente válido
println!("Method: {}", request.method);
println!("Path: {}", request.path);
```

Essa estrutura separa claramente **parsing** (pode falhar) de **processamento** (assume dados válidos).

### Passo 6: Parse da Request Line

#### 💭 Pensamento do Engenheiro

**Onde estamos?**

No Passo 5, criamos a estrutura `HttpRequest` e a assinatura do método `parse()`. Agora temos o "molde" que queremos preencher, mas a função ainda está vazia (`todo!()`). Conseguimos ler a primeira linha da requisição (isso vem do Passo 4 que fizemos em `server.rs`), mas ainda não extraímos as informações dessa linha nem validamos se são legítimas.

**O que preciso agora?**

Preciso **parsear e validar** a request line. Essa linha contém 3 componentes críticos: método HTTP, path e versão. Cada um precisa de validação rigorosa antes de aceitar a requisição. Não posso simplesmente confiar no que o cliente envia — preciso verificar que o método é permitido, que a versão é suportada, e **especialmente** que o path não contém tentativas de ataque. Se qualquer validação falhar, devo rejeitar imediatamente com erro 400. Só depois de todas as validações passarem, posso prosseguir para headers e body.

**Por que validação de path é crítica?**

Path traversal é um dos ataques mais comuns e perigosos em servidores web. O atacante tenta manipular o path para acessar arquivos fora do diretório público:

```
GET /../../../etc/passwd HTTP/1.1     ← Ataque clássico
GET /api/users%2e%2e%2fetc/passwd     ← URL encoding bypass
GET //etc/passwd HTTP/1.1              ← Absolute path abuse
```

**Validação básica (INSUFICIENTE):**

```rust
if path.contains("..") || path.contains("//") {  // ❌ Fácil bypass
    return Err("Invalid path");
}
```

Problemas:

- **URL encoding bypass:** `%2e%2e` = `..` (depois de decode)
- **Não valida paths absolutos:** `/etc/passwd` passa
- **Não normaliza:** `./././etc/passwd` passa

**Validação production-ready (CORRETO):**

Usar `canonicalize()` da std lib para garantir segurança real:

1. **Canonicalização:** Transforma path relativo em absoluto normalizado (resolve `.`, `..`, symlinks)
2. **Verificação de prefixo:** Garante que o path final ainda está dentro do diretório base

**Como funciona:**

- `PathBuf::from("./public")` — Define diretório base permitido
- `.join(path)` — Combina base + path do cliente
- `.canonicalize()` — Resolve `..`, `.`, symlinks → path absoluto real no disco
- `.starts_with(base)` — Verifica que path final ainda está dentro da base

**Por que isso previne ataques?**

- `canonicalize()` **resolve** `..`, `.`, symlinks → path absoluto real
- `starts_with()` **verifica** que path final ainda está em `/caminho/para/public`
- Impossível escapar: qualquer tentativa de `..` é resolvida e depois detectada

**Exemplo:**

```
Base: /var/www/public
Request: /../../../etc/passwd

Após canonicalize: /etc/passwd
starts_with(/var/www/public)? NÃO → REJEITA ✅
```

### Passo 7: Parse de Headers

#### 💭 Pensamento do Engenheiro

**Onde estamos?**

No Passo 6, implementamos o parsing da request line — método, path e versão já estão validados e armazenados na struct. O parser consegue extrair a primeira linha da requisição e rejeitar tentativas de path traversal. Mas isso é só o começo. Após a request line, vêm os **headers HTTP** — linhas com metadados que controlam comportamento da requisição: tipo de conteúdo, tamanho do body, autenticação, cache, etc. Se eu ignorar headers, não consigo processar POST (preciso saber tamanho do body), não consigo fazer autenticação (preciso do `Authorization`), e não consigo responder corretamente (preciso do `Accept` para saber formato esperado).

**O que preciso agora?**

Preciso ler todas as linhas de headers até encontrar a **linha vazia** que separa headers do body. Cada header tem formato `Chave: Valor`, e preciso parsear isso em um HashMap para lookup eficiente. Mas headers são **território hostil** — atacantes podem enviar milhares de headers, headers gigantes, ou headers malformados para causar DoS. Não posso simplesmente ler tudo que vier — preciso de **limites de segurança** rigorosos.

**Formato dos headers HTTP:**

```
GET /api/users HTTP/1.1        ← Request line (já parseada)
Host: example.com              ← Header 1
Content-Type: application/json ← Header 2
Content-Length: 42             ← Header 3
Authorization: Bearer_escapa_gitleaks_ abc123   ← Header 4
                               ← Linha vazia (fim dos headers)
{"name":"Alice"}               ← Body (Passo 8)
```

Cada linha tem formato `Key: Value` (separador é `: ` com espaço). Headers podem ter espaços ao redor do valor (`Content-Length:  42  ` é válido), então preciso fazer trim.

**Por que headers são vetores de ataque?**

Três ataques clássicos:

1. **Slowloris:** Enviar headers muito lentamente para ocupar conexões
2. **Header bomb:** Enviar milhares de headers para esgotar memória
3. **Giant header:** Enviar header de 1GB para travar parser

**Proteções necessárias:**

- **Limite por linha:** `MAX_LINE_SIZE` = 8KB (mesma constante da request line)
- **Limite de quantidade:** `MAX_HEADERS` = 50 headers (mais que suficiente para uso legítimo)
- **Timeout de leitura:** Se cliente demora muito, desconecta (Passo futuro)

**Como identificar o fim dos headers?**

HTTP usa **linha vazia** (`\r\n\r\n`) para separar headers do body:

```
Content-Length: 42\r\n    ← Último header
\r\n                      ← Linha vazia = fim dos headers
{"data":"here"}           ← Body começa aqui
```

No código:

```rust
loop {
    let mut line = String::new();
    reader.read_line(&mut line)?;

    if line.trim().is_empty() {  // Linha vazia = fim
        break;
    }

    // Parsear "Key: Value"
}
```

**Por que HashMap já foi criado no Passo 5?**

No Passo 5, definimos `headers: HashMap<String, String>` na struct. Agora vamos **preenchê-la**. HashMap é ideal porque:

- Headers são consultados por nome: `request.headers.get("content-type")`
- Lookup é O(1) em vez de O(n) de um Vec
- Duplicatas são automaticamente sobrescritas (comportamento correto: última vence)

**Validação específica de método:**

POST/PUT exigem `Content-Type` (servidor precisa saber formato do body). GET não tem body, então não precisa. Essa validação acontece **depois** de ler todos os headers:

```rust
if method == "POST" && !headers.contains_key("content-type") {
    return Err("Content-Type required for POST");
}
```

**Fluxo de leitura:**

1. Loop: ler linha com limite (`MAX_LINE_SIZE`)
2. Se linha vazia → break (fim dos headers)
3. Split por `:` → `("Content-Length", " 42")`
4. Trim espaços → `("Content-Length", "42")`
5. Inserir no HashMap
6. Se `headers.len() > MAX_HEADERS` → erro de segurança
7. Após loop: validar headers obrigatórios para o método

Essa estrutura garante que nunca vamos consumir memória ou CPU infinita mesmo com cliente malicioso.

### Passo 7.1: Otimizações de Performance e Segurança

#### 💭 Pensamento do Engenheiro

**Onde estamos?**

O parser de headers do Passo 7 está funcional e protegido contra ataques básicos (header bomb, giant headers). Validamos tamanho de linha, quantidade máxima, e normalizamos chaves. **O código funciona e está seguro contra os ataques que testamos.** Mas após revisão de código sênior, identificamos dois gargalos de performance que, embora não críticos em baixa escala, tornam-se relevantes sob carga real (milhares de requisições/segundo) ou ataques DoS sofisticados.

**Problema 1: Ordem das Operações — Desperdício de I/O**

Atualmente, a validação de path (linhas ~53-72 em `request.rs`) acontece **antes** de ler os headers:

```
1. Parse request line ✓
2. Validar método ✓
3. Validar versão ✓
4. Chamar env::var("PUBLIC_DIR") ← Syscall
5. Chamar canonicalize() ← Syscall de filesystem (I/O de disco)
6. Validar path traversal ✓
7. Loop de headers ✓
```

**Cenário de ataque:**

```http
GET /valid/path.html HTTP/1.1
Header1: value
Header2: value
[... 98 headers mais ...]
Content-Length: 999999999999
```

O que acontece:

- Servidor faz **syscalls de disco** (canonicalize) para validar path
- **Depois** descobre que headers são maliciosos (body size gigante)
- Desperdiçou I/O custoso que podia ter sido evitado rejeitando headers primeiro

**Por que isso importa?**

- `canonicalize()` é uma operação **bloqueante de I/O**
- Em SSDs: ~100-500 microsegundos
- Em HDDs: ~5-20 milissegundos
- Sob ataque com 1000 req/s maliciosas: desperdício significativo de I/O

**Solução:** Inverter ordem — validar **protocolo HTTP completo** antes de tocar filesystem:

```
1. Parse request line ✓
2. Validar método (in-memory) ✓
3. Validar versão (in-memory) ✓
4. Loop de headers (in-memory + network I/O) ✓
```

**Problema 2: Syscalls Repetidas — env::var e canonicalize**

# Checklist de Engenharia: Infraestrutura e Otimização de I/O

## 🚀 Problema: Syscalls Repetidas (`env::var` e `canonicalize`)

No loop de requisições, buscar variáveis de ambiente e resolver caminhos no sistema de arquivos é um desperdício inaceitável de ciclos de CPU. Estamos falando de atravessar o limite do Kernel milhares de vezes para obter uma informação que é estática.

### 📊 Impacto Real

- **Custo por Req:** De 100 a 500 μs desperdiçados em operações bloqueantes ou desnecessárias.
- **Escala:** Em 10k req/s, você satura o CPU apenas com gerenciamento de paths, impedindo o throughput real da aplicação.

---

## 🛠️ Solução: Singleton de Configuração Imutável

A estratégia é o **Fail-Fast**: resolvemos tudo no boot. Se o diretório estiver errado, o binário nem sobe. O estado é armazenado em uma struct `ServerConfig` e compartilhado por referência.

### 📂 Passo 1: Implementação da Struct `ServerConfig`

**Arquivo:** `backend/shared/src/lib.rs`

```rust
use std::path::PathBuf;
use std::env;

pub struct ServerConfig {
    /// Caminho absoluto resolvido no boot (zero custo em runtime)
    pub base_canonical: PathBuf,
}

impl ServerConfig {
    /// Construtor soberano: resolve dependências do SO uma única vez.
    pub fn new(custom_dir: Option<String>) -> Result<Self, String> {
        // Prioridade: Argumento direto > Variável de Ambiente > Default "public"
        let dir_name = custom_dir
            .or_else(|| env::var("PUBLIC_DIR").ok())
            .unwrap_or_else(|| "public".to_string());

        // Syscall canonicalize(): resolve symlinks e valida existência
        let base_canonical = PathBuf::from(&dir_name)
            .canonicalize()
            .map_err(|e| format!("ERRO CRÍTICO: Caminho '{}' inacessível: {}", dir_name, e))?;

        Ok(Self { base_canonical })
    }
}
```

```rust
use crate::ServerConfig;

impl HttpRequest {
    pub fn parse(
        reader: &mut BufReader<TcpStream>,
        config: &ServerConfig  // ← Nova dependência injetada
    ) -> Result<Self, String> {
        // Parse request line + headers primeiro (validação in-memory)
        let (method, path, version) = parse_request_line(reader)?;
        validate_method(&method)?;
        validate_version(&version)?;
        let headers = parse_headers(reader)?;

        // Validação de path DEPOIS (filesystem I/O apenas se HTTP for válido)
        validate_path_traversal(&path, &config.base_canonical)?;

        Ok(HttpRequest { method, path, headers, body: String::new() })
    }
}

// Substituir validação antiga por:
fn validate_path_traversal(path: &str, base_canonical: &PathBuf) -> Result<(), String> {
    let requested = base_canonical.join(path.trim_start_matches('/'));
    let canonical = requested.canonicalize()
        .map_err(|_| "Invalid path or file not found".to_string())?;

    if !canonical.starts_with(base_canonical) {
        return Err("Path traversal detected".to_string());
    }
    Ok(())
}
```

````
### Passo 9.2: Configurar Timeouts (Proteção Slowloris)

#### 💭 Pensamento do Engenheiro

**Onde estamos?**

Nos passos anteriores, implementamos validações de tamanho: `MAX_LINE_SIZE` protege contra headers gigantes, `MAX_HEADERS` protege contra header bomb, `MAX_BODY_SIZE` protege contra payloads enormes. Essas proteções funcionam contra ataques que tentam **esgotar memória** enviando dados massivos. Mas existe outro tipo de ataque igualmente perigoso: **Slowloris**.

**O que é Slowloris?**

Slowloris é um ataque de negação de serviço (DoS) que **não precisa de largura de banda**. Em vez de enviar dados massivos rapidamente, o atacante envia dados **muito lentamente**:

```
Atacante conecta ao servidor
Envia: "GET / HTTP/1.1\r\n"
[espera 10 segundos]
Envia: "Host: example.com\r\n"
[espera 10 segundos]
Envia: "User-Agent: Mozilla\r\n"
[espera 10 segundos]
... nunca completa a requisição
```

**Por que isso é perigoso?**

Servidores têm **número limitado de conexões simultâneas** (geralmente 100-1000). Se cada conexão fica **travada esperando** o cliente terminar de enviar dados, rapidamente todas as conexões são ocupadas. Clientes legítimos não conseguem mais conectar → servidor offline.

**Matemática do ataque:**

- Servidor permite 100 conexões simultâneas
- Atacante abre 100 conexões e envia dados **1 byte por minuto**
- `MAX_LINE_SIZE` não protege (nunca ultrapassa 8KB)
- `MAX_HEADERS` não protege (nunca ultrapassa 50 headers)
- Servidor fica **travado** esperando eternamente

**Solução: Timeouts no Socket**

TCP sockets têm dois timeouts configuráveis:

1. **Read timeout:** Quanto tempo esperar por dados do cliente antes de desistir
2. **Write timeout:** Quanto tempo esperar para enviar dados ao cliente antes de desistir

Se configurarmos `read_timeout = 5 segundos`, qualquer operação de leitura que demore mais de 5 segundos automaticamente retorna erro e a conexão é fechada.

**Onde aplicar os timeouts?**

Timeouts devem ser configurados **no TcpStream antes de criar o BufReader**. BufReader herda as configurações do stream subjacente:

```rust
fn handle_connection(mut stream: TcpStream) {
    // 1. PRIMEIRO: configurar timeouts no stream bruto
    stream.set_read_timeout(Some(Duration::from_secs(5))).unwrap();
    stream.set_write_timeout(Some(Duration::from_secs(5))).unwrap();

    // 2. DEPOIS: criar BufReader (que herda os timeouts)
    let mut reader = BufReader::new(&mut stream);

    // 3. Agora qualquer read_line() tem timeout automático
    match HttpRequest::parse(&mut reader) { ... }
}
```

**Por que 5 segundos?**

- Rede lenta legítima: 1-2 segundos para enviar request completa
- Conexão 3G ruim: ~3 segundos
- Slowloris: tenta durar minutos/horas
- **5 segundos:** balanceio entre tolerância a redes ruins e proteção contra ataques

**O que acontece quando timeout expira?**

`read_line()` retorna `io::Error` com tipo `ErrorKind::TimedOut`. O código de error handling já existente (`match HttpRequest::parse()`) automaticamente fecha a conexão e libera o slot para próximo cliente.

**Validação de segurança:**

Após implementar, testar com:

```bash
# Simular Slowloris: enviar request line lentamente
(echo -n "GET / HTTP/1.1\r\n"; sleep 10; echo "Host: localhost\r\n\r\n") | nc localhost 8080
```

Servidor deve retornar erro após 5 segundos, não após 10.
````
