## 1.5 API de HttpRequest

### Passo 9.4: Métodos Utilitários em HttpRequest

#### 💭 Pensamento do Engenheiro

**Onde estamos?**

O parser de `HttpRequest` está completo: valida request line, headers, body, path traversal e timeouts. A struct tem campos públicos (`method`, `path`, `headers`, `body`) e qualquer parte do sistema pode acessá-los diretamente. Isso funciona, mas cria um problema que vai aparecer quando começarmos a escrever os handlers na camada de lógica.

**O problema que ainda não sentimos**

Observe o código que o plano de `02-camada-logica.md` (Passo 16) já esboça:

```rust
let content_type = req.headers.get("content-type")
    .ok_or("Content-Type required")?;
if !content_type.contains("application/json") {
    return HttpResponse::bad_request();
}
```

Isso parece inofensivo agora. Mas quando tivermos 3, 4, 5 handlers diferentes, cada um vai repetir esse padrão — cada um vai saber que o header foi normalizado para lowercase, cada um vai fazer `.contains()` na string, cada um vai precisar lembrar da string mágica `"content-type"`. Se um dia quisermos mudar como validamos content type (ex: aceitar `text/plain` em alguns endpoints), precisamos achar todos os lugares no código.

**O princípio violado: Tell, Don't Ask**

O padrão atual é **Ask** (perguntar os dados e decidir fora):

```rust
// Handler pergunta dados internos e decide
if req.headers.get("content-type").map_or(false, |v| v.contains("application/json")) { ... }
```

O padrão melhor é **Tell** (pedir ao objeto que responda):

```rust
// Handler pergunta ao objeto
if req.is_json() { ... }
```

A diferença: no segundo caso, toda a lógica de "o que é JSON" fica em um lugar — dentro de `HttpRequest`. Se mudar, muda em um lugar.

**Três métodos de alto valor**

Analisando o que os handlers vão precisar (Passos 16-18 de `02-camada-logica.md`), três padrões se repetem:

1. **`is_json()`** — verificar se content-type é JSON antes de parsear body. Usado em todo endpoint POST que aceita JSON.

2. **`header(key)`** — acessar header de forma idiomática, retornando `Option<&str>`. Evita expor o HashMap diretamente e remove a necessidade do caller saber que os headers foram normalizados para lowercase.

3. **`file_extension()`** — identificar a extensão do arquivo pedido para determinar o Content-Type da resposta. Usado no handler de arquivos estáticos (Passo 13 em `01.4-response-builder.md`) para mapear `.html` → `text/html`, `.css` → `text/css`, etc.

**Por que não agora já seria custoso?**

Se esperarmos para adicionar esses métodos depois que os handlers estiverem escritos, vamos ter que:
1. Encontrar todos os `req.headers.get(...)` espalhados
2. Substituir um por um sem quebrar nada
3. Testar tudo de novo

Adicionar antes é barato: modifica apenas `request.rs`, nenhum handler existe ainda para quebrar.

**A transição futura mencionada (`&'static str`)**

O arquivo `01.4-response-builder.md` já usa `&'static str` para `content_type` na struct `HttpResponse`. Futuramente, quando tivermos otimizações de memória (ver `05-otimizacoes-avancadas/`), métodos como `header()` retornando `Option<&str>` (lifetime da struct) serão mais fáceis de adaptar do que acessos diretos ao HashMap — porque o contrato público não muda, só a implementação interna.

**O que NÃO fazer aqui**

Não transformar `HttpRequest` em uma "god struct" com dezenas de métodos. A regra: só adicionar métodos que **múltiplos handlers vão usar**. Lógica específica de um endpoint (ex: extrair CPF do body JSON) fica no handler, não aqui.

#### Checklist

- [ ] Em `backend/shared/src/http/request.rs`, adicionar bloco `impl HttpRequest` com os métodos abaixo (separado do `impl` do `parse`):

- [ ] **`header()`** — acesso normalizado a qualquer header:
  ```rust
  pub fn header(&self, key: &str) -> Option<&str> {
      self.headers.get(&key.to_lowercase()).map(|v| v.as_str())
  }
  ```
  **Por que:** encapsula o detalhe de que headers são lowercase internamente. Caller não precisa saber.

- [ ] **`is_json()`** — verificação semântica de content-type:
  ```rust
  pub fn is_json(&self) -> bool {
      self.header("content-type")
          .map_or(false, |v| v.contains("application/json"))
  }
  ```
  **Por que:** elimina string mágica `"content-type"` e lógica `.contains("application/json")` espalhadas nos handlers. Centraliza a definição de "o que é uma request JSON".

- [ ] **`file_extension()`** — extração da extensão do path:
  ```rust
  pub fn file_extension(&self) -> Option<&str> {
      self.path
          .rsplit('.')
          .next()
          .filter(|ext| !ext.contains('/'))
  }
  ```
  **Por que:** o handler de arquivos estáticos (Passo 13) precisa mapear extensão → Content-Type. `.rsplit('.')` é mais correto que `.split('.').last()` porque começa pelo final — lida corretamente com paths como `/files/archive.tar.gz` retornando `"gz"`. O `.filter(|ext| !ext.contains('/'))` garante que um path como `/no-extension/file` não retorna `"file"` como extensão.

- [ ] Compilar sem warnings: `cargo check`

- [ ] Validar `header()` com teste manual:
  ```bash
  # Com servidor rodando, verificar nos logs que req.header("content-type")
  # retorna valor quando enviado
  curl -H "Content-Type: application/json" http://localhost:8080/index.html
  ```

- [ ] Validar `is_json()` — adicionar temporariamente em `server.rs` para inspeção:
  ```rust
  println!("Is JSON: {}", req.is_json());
  ```
  ```bash
  curl -H "Content-Type: application/json" -X POST http://localhost:8080/  # → Is JSON: true
  curl http://localhost:8080/index.html                                     # → Is JSON: false
  ```

- [ ] Validar `file_extension()`:
  ```bash
  # /index.html → Some("html")
  # /style.css  → Some("css")
  # /           → None
  # /no-ext     → None (sem ponto no path)
  ```

- [ ] Remover prints temporários após validação

#### Resultado esperado

O código nos handlers futuros será:

```rust
// Antes (sem os métodos)
let ct = req.headers.get("content-type").map_or("", |v| v.as_str());
if !ct.contains("application/json") { ... }

// Depois (com os métodos)
if !req.is_json() { ... }
```

Mais legível, mais seguro, sem strings mágicas espalhadas.
