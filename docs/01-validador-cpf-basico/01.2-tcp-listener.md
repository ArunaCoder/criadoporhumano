## 1.2 Implementar TCP Listener

### Passo 3: Servidor Básico

#### 💭 Pensamento do Engenheiro

**Onde estamos?**

Nos passos anteriores (Passo 1-2), definimos a estrutura de módulos do projeto: criamos `server.rs` (responsável por aceitar conexões), `request.rs` (vai parsear requisições) e `response.rs` (vai construir respostas). Essa organização está no lugar, mas os arquivos ainda estão vazios — são apenas declarações de módulo. Não tenho código executável ainda. Se eu rodar `cargo run`, o compilador vai reclamar que não existe função `main()`.

**O que preciso agora?**

Preciso transformar essas declarações em um **servidor funcional** que realmente escute em uma porta e aceite conexões TCP. Isso significa implementar a camada mais baixa da rede: antes de entender HTTP, preciso entender TCP. Meu objetivo aqui é simples: fazer o servidor **ficar vivo** em `127.0.0.1:8080`, aceitar quando um cliente conectar, e não morrer em situações adversas (clientes lentos, ataques DoS). Se conseguir isso, terei a fundação necessária para depois adicionar o parsing HTTP. Primeiro, servidor TCP básico; depois, protocolo HTTP.

**Por que `127.0.0.1:8080` especificamente?**

Um servidor TCP precisa de um **endereço IP** e uma **porta** para escutar. Essa escolha tem implicações de segurança e praticidade.

**Por que `127.0.0.1` (localhost)?**

Três opções existem para o endereço:

1. **`0.0.0.0`** — Escuta em **todas as interfaces de rede**
   - Aceita conexões de qualquer lugar: localhost, rede local, internet
   - Perigoso em desenvolvimento: expõe servidor para toda a rede
   - Usado em produção (atrás de firewall/proxy)

2. **`127.0.0.1` (nossa escolha)** — Escuta **apenas em loopback**
   - Aceita conexões apenas do próprio computador
   - Seguro: ninguém na rede pode acessar o servidor
   - Ideal para desenvolvimento e testes locais

3. **`192.168.x.x` (IP da rede local)** — Escuta em interface específica
   - Útil para testar em múltiplos dispositivos na mesma rede
   - Requer descobrir IP manualmente (`ifconfig`/`ipconfig`)

Para MVP/desenvolvimento, `127.0.0.1` é a escolha mais segura e conveniente. Em produção, mudamos para `0.0.0.0` e configuramos firewall.

**Por que porta `8080`?**

As portas TCP vão de **0 a 65535**, divididas em 3 faixas:

- **0-1023: Well-known ports** — Reservadas pelo sistema (precisam de root/admin)
  - 80: HTTP padrão (requer sudo/administrador)
  - 443: HTTPS padrão (requer sudo/administrador)
  - 22: SSH, 21: FTP, etc.

- **1024-49151: Registered ports** — Usadas por aplicações conhecidas
  - 3000: Node.js dev server (Next.js, React)
  - 5432: PostgreSQL
  - 8080: **HTTP alternativo** (nossa escolha)

- **49152-65535: Dynamic/private ports** — Portas efêmeras

Escolhemos **8080** porque:

- Convenção universal para servidores HTTP de desenvolvimento
- Não requer privilégios de root/administrador (> 1024)
- Fácil de lembrar (80 é HTTP oficial, 8080 é "HTTP de desenvolvimento")
- Evita conflito com porta 80 (pode já estar em uso por Apache/Nginx)
- Todos os desenvolvedores reconhecem `localhost:8080` instantaneamente

**Alternativas comuns:**

- `3000`: Usado por frameworks Node.js (Next.js, Create React App)
- `5000`: Usado por Flask (Python)
- `8000`: Usado por Django (Python)
- `8081/8082`: Quando já tem algo rodando em 8080

**O que um servidor TCP precisa fazer?**

Um servidor HTTP (antes de entender HTTP) precisa de 4 capacidades fundamentais:

1. **Ouvir** em um endereço/porta (ex: `127.0.0.1:8080`)
2. **Aceitar** múltiplas conexões sequencialmente
3. **Proteger-se** contra clientes mal-comportados (timeouts)
4. **Delegar** cada conexão para processamento

**Como organizar essas capacidades?**

Rust oferece `std::net::TcpListener` que resolve os dois primeiros problemas. Organizamos o código em duas funções:

- `start_server(addr)`: cria o listener, entra em loop infinito aceitando conexões
- `handle_connection(stream)`: processa uma conexão individual

**Por que loop infinito ao invés de processar uma conexão e sair?**

Um servidor precisa **ficar vivo** aceitando múltiplas conexões. Três abordagens existem:

1. **Loop infinito + blocking I/O** (nossa escolha): uma conexão por vez, simples
2. **Thread pool**: uma thread por conexão, complexidade moderada
3. **Async/await (Tokio)**: milhares de conexões simultâneas, alta complexidade

Para MVP com < 10 requisições/segundo, blocking I/O é suficiente e **dramaticamente mais simples** (zero dependencies, zero runtime overhead).

**Por que timeouts são críticos?**

Sem timeouts, um cliente malicioso pode:

- **Slowloris attack:** abrir conexão e nunca enviar dados (trava o servidor eternamente)
- **Slow POST:** enviar dados byte-by-byte (ocupa recursos infinitamente)

Rust não adiciona timeouts por padrão. **É responsabilidade do desenvolvedor** configurar timeouts de leitura e escrita (5 segundos cada). Após esse tempo sem atividade, o SO encerra a conexão automaticamente. Isso libera recursos e previne DoS.

**Como funciona o fluxo de execução?**

O servidor segue 5 passos:

1. **Bind:** Vincula-se a um endereço/porta (falha se já estiver em uso)
2. **Loop infinito:** Fica eternamente aguardando conexões (só sai em erro fatal)
3. **Accept:** Cada iteração aceita uma nova conexão individual
4. **Timeout:** Configura limites de tempo para leitura e escrita
5. **Delegate:** Repassa a conexão para função especializada processar

**Detalhe arquitetural: por que iteradores são eficientes aqui?**

O método `incoming()` retorna um **iterador preguiçoso**. Cada iteração **bloqueia** até uma nova conexão chegar. Isso significa:

- Zero uso de CPU enquanto aguarda conexões
- Não precisa de `sleep()` ou polling manual
- O SO acorda o processo quando cliente conecta

Essa é a **magia do blocking I/O**: simplicidade com eficiência razoável para cargas baixas/médias.

- [x] Implementar loop infinito: `for stream in listener.incoming() { ... }`

### Passo 4: Handler Básico

#### 💭 Pensamento do Engenheiro

**Onde estamos?**

No Passo 3, implementei um servidor TCP que aceita conexões: `TcpListener::bind()` vincula à porta, o loop `for stream in listener.incoming()` aceita clientes, e configurei timeouts (5 segundos) para proteger contra ataques. Se eu rodar `cargo run` e abrir `curl http://localhost:8080`, a conexão é aceita com sucesso — mas o servidor não faz nada com ela ainda. O `TcpStream` chega na função `handle_connection()`, mas essa função está vazia. O cliente fica esperando resposta e eventualmente desiste (timeout). Tenho a **infraestrutura de conexão**, mas falta **processar os dados**.

**O que preciso agora?**

Preciso **ler dados** desse `TcpStream`. Quando um cliente faz `GET / HTTP/1.1`, esses bytes estão viajando pela rede e chegando no meu servidor. TCP me entrega esses bytes brutos, mas eles estão em um formato inconveniente: podem vir fragmentados (1 byte por vez ou 1000 de uma vez), precisam ser convertidos para texto UTF-8, e preciso saber onde cada "linha" termina (HTTP usa `\r\n`). Antes de parsear HTTP completo (isso vem no Passo 5), preciso validar que consigo **simplesmente ler a primeira linha** da requisição e printar no console. Isso prova que a leitura de dados funciona. Depois disso, posso expandir para ler headers, body, etc.

**O que o handler de conexão precisa fazer?**

Após aceitar uma conexão, o handler tem 3 responsabilidades:

1. **Receber** bytes brutos da rede
2. **Interpretar** esses bytes como texto (UTF-8)
3. **Proteger-se** contra dados maliciosos ou excessivos

**Por que organizar a leitura de dados?**

Ler bytes brutos de um socket é trabalhoso e propenso a erros. Três problemas fundamentais:

1. **Fragmentação:** Dados chegam em pedaços imprevisíveis
   - Cliente pode enviar `"GET / HTTP/1.1\r\n"` em 1 pacote ou em 17 pacotes de 1 byte cada
   - `stream.read()` pode retornar 5 bytes, depois 3, depois 9... você precisa juntar manualmente

2. **Delimitação:** Como saber onde uma linha termina?
   - HTTP usa `\r\n` (CRLF) para separar linhas
   - Ler byte-por-byte procurando `\n` é ineficiente (1 syscall por byte)
   - Ler tudo de uma vez desperdiça memória e não resolve fragmentação

3. **Conversão:** Bytes não são String automaticamente
   - TCP entrega `[71, 69, 84, 32, 47]` (bytes)
   - Você precisa converter para `"GET /"` (UTF-8)
   - Precisa lidar com UTF-8 inválido (bytes aleatórios)

**Sem abstração, você escreve ~50 linhas de código apenas para ler uma linha de texto.** Esse código precisa de buffer circular, detecção de CRLF, conversão UTF-8, validação... tudo manual.

**Com abstração (BufReader), você escreve 2 linhas.** A biblioteca padrão já resolveu esses 3 problemas de forma testada e eficiente.

> **Nota:** Para discussão sobre o dilema pedagógico de usar BufReader vs implementar buffer manualmente, ver seção "5. BufReader vs Parsing Manual de Bytes" em [99-decisoes-metricas.md](99-decisoes-metricas.md).

**Como organizar a leitura de dados?**

Rust oferece duas abordagens:

- **Leitura bruta:** `stream.read(&mut buffer)` — você controla buffer manualmente
- **BufReader (nossa escolha):** adiciona camada de buffer interno e métodos convenientes

Escolhemos `BufReader` porque ele oferece `read_line()`, que:

- Lê até encontrar `\n` (newline)
- Reconstrói a String automaticamente
- Gerencia o buffer interno de forma eficiente

**Por que lemos apenas UMA linha?**

Neste passo, estamos construindo o handler básico incrementalmente. A estrutura de uma requisição HTTP é:

```
GET /api/users HTTP/1.1        ← Linha 1: request line (isso!)
Host: example.com               ← Linha 2+: headers
Content-Type: application/json  ← Mais headers...
                                ← Linha vazia (separador)
{"data":"..."}                  ← Body (opcional)
```

**Por enquanto, só precisamos da primeira linha** porque ela contém as informações essenciais:

- **Método:** GET, POST, HEAD, OPTIONS
- **Path:** qual recurso o cliente quer (/, /api/validate, etc.)
- **Versão:** HTTP/1.1 ou HTTP/1.0

Com essas 3 informações, já podemos validar se a requisição é bem-formada antes de continuar processando.

**E os headers? E o body?**

Eles vêm nos passos seguintes:

- **Passo 5-7:** Implementar parser completo que lê request line + headers + body
- **Passo 4 (atual):** Apenas validar que conseguimos aceitar conexão e ler a primeira linha

Essa abordagem incremental permite:

1. Testar conexão TCP isoladamente (Passo 3)
2. Testar leitura de dados isoladamente (Passo 4)
3. Implementar parsing completo depois (Passos 5-9)

**Por que uma linha é suficiente para validar?**

Se não conseguimos ler nem a primeira linha corretamente, não adianta tentar ler headers e body. Validamos do mais simples para o mais complexo:

- ✅ Conexão funciona? (Passo 3)
- ✅ Conseguimos ler texto? (Passo 4)
- ⏭️ Conseguimos parsear protocolo HTTP completo? (Passos 5-9)

**Por que limitar tamanho de linha é crítico?**

Sem limites, um ataque trivial:

```
Cliente malicioso envia: "GET /" + ("A" repetido 1GB) + "\r\n"
```

Sem proteção, `read_line()` aloca 1GB de RAM. Com 10 conexões simultâneas = **10GB consumidos = OOM (Out Of Memory) = servidor morre**.

Esse é um **ataque de negação de serviço (DoS) via exaustão de memória**. Custo do ataque: $0. Dano: servidor offline.

**Como funciona a proteção?**

A proteção tem 3 camadas:

1. **Limitar bytes lidos:** usar `take(MAX_LINE_SIZE)` — só permite ler N bytes do stream
2. **Validar após leitura:** verificar se buffer atingiu o limite (indica ataque)
3. **Rejeitar requisição:** retornar erro 400 (Bad Request) e fechar conexão

O `take()` cria um **adaptador** que envolve o reader. Quando atinge o limite, passa a retornar 0 bytes (EOF simulado). Isso previne alocação infinita.

**Por que 8KB especificamente?**

Análise de requisições HTTP reais:

- **Request line típica:** 50-200 bytes (`GET /api/users?id=123 HTTP/1.1`)
- **Request line máxima razoável:** ~2KB (URL complexa com query params)
- **Nginx/Apache usam:** 4KB-8KB como padrão

Escolhemos **8KB (8192 bytes)** porque:

- Acomoda URLs legítimas complexas
- Previne consumo excessivo (1000 conexões = 8MB, aceitável)
- É potência de 2 (otimização de alocação de memória)

**Diferença entre timeout e limite de tamanho:**

- **Timeout (Passo 3):** protege contra clientes **lentos** (enviam dados, mas devagar)
- **Limite de tamanho (Passo 4):** protege contra clientes **maliciosos** (enviam dados gigantes rapidamente)

Ambos são necessários para defesa em profundidade.
